## 1. Overview

Site Chat separates **who the visitor is** from **which browser session they are in** and **which conversation they are chatting in**. This document describes the identity model shipped as the visitor identity + context foundation.

| Concept | Table | Lifetime | Purpose |
|---------|-------|----------|---------|
| **Visitor (contact)** | `contacts` | Durable, workspace-scoped | Stable identity record (anonymous or identified) |
| **Session** | `visitor_sessions` | Browser-scoped (~30 days TTL) | Auth token, device/page context for one browser |
| **Conversation** | `conversations` | Messaging thread | Open/pending/resolved chat linked to a session (and usually a contact) |
| **Page view** | `visitor_page_views` | Bounded trail | Recent URLs/titles for operator context |

Contacts are the visitor identity. The product language says “visitor”; the schema keeps the table name `contacts` (see ADR-003).

## 2. Visitor vs session vs conversation

### 2.1 Contact (visitor identity)

A `contacts` row is the durable visitor record within one workspace:

- `app_private.ensure_visitor_contact` **always creates a new anonymous contact**. There is no lookup-by-`public_id` path anywhere in the system (see §3).
- A new session reuses an **existing** contact only when it presents a valid `continuity_token` that hashes to a stored `continuity_token_hash` (§4), or when it resumes via an existing session's Bearer token.
- May later gain `name`, `email`, `phone` / `phone_e164`, and `custom_attributes_json` via unsigned identify (§7.1) or operator edit (§7.3).
- Email uniqueness is **per workspace** (`(workspace_id, lower(email))` when email is present). Unsigned identify never searches by email — it only enforces the uniqueness constraint on write (see §7.1).
- `visit_count` increments only when a **new** session links to an existing contact via a valid continuity token.
- `first_seen_at` / `last_seen_at` track identity lifetime (visitor activity only — see §12); session `last_seen_at` tracks browser activity.

### 2.2 Session

A `visitor_sessions` row binds one browser (or embed instance) to a hashed session token:

- Token is opaque (32 random bytes, base64url); only `session_token_hash` (SHA-256) is stored. It is **not** a JWT and carries no embedded claims — see §10.
- Sent by the client as `Authorization: Bearer <session_token>` on every widget API request.
- Carries page/device/UTM context for the current visit (no raw IP, no raw User-Agent string).
- Optionally links to `contact_id`.
- Expires (default ~30 days from last activity); used by widget APIs for authorization.

### 2.3 Conversation

A conversation is the messaging thread:

- Always tied to a `visitor_session_id`.
- Usually denormalizes `contact_id` for inbox queries.
- Unsigned identify (not page-view) bumps `conversations.updated_at` for this session's open/pending rows to refresh the operator UI (see §8).

```
Host page ──► Widget ──► Session (Bearer token)
                              │
                              ├──► Contact (public_id: display only, PII, attributes,
                              │             continuity_token_hash: real binder)
                              │
                              └──► Conversation(s) ──► Messages
                                        │
                                        └── recent page views (via contact or session)
```

## 3. `public_id` semantics — display/reference only

`contacts.public_id` is a **display and correlation id**. It is generated by a column `DEFAULT` on every `contacts` INSERT (`'vis_' || encode(gen_random_bytes(16), 'hex')`) — there is no code path that mints it separately or resolves a contact *by* it.

| Property | Rule |
|----------|------|
| Format | `vis_` + 32 lowercase hex characters (`^vis_[a-f0-9]{32}$`) |
| Generation | `DEFAULT` expression on `contacts.public_id`, cryptographically random (`gen_random_bytes(16)`); not derived from email, IP, or sequence |
| Scope | Unique per `(workspace_id, public_id)`; same visitor in another workspace gets a different id |
| **Not a secret** | Safe to log, display in the operator UI, and store in widget `localStorage` |
| **Not authorization** | Never checked by any RPC to look up, resume, bind, or otherwise authorize a session or contact. **Leaking a `public_id` cannot enable session takeover, contact binding, or PII disclosure beyond what is already visible wherever the id was leaked.** |
| Enumeration | Not guessable; knowing one id does not reveal others; there is no lookup API keyed on it |
| Not identity alone | Still requires workspace context; never treat as a global user id |

Internal UUID `contacts.id` remains the primary key for FKs. `public_id` is the client-facing correlation identifier — the durable, secret-bearing counterpart is the continuity credential (§4).

## 4. Continuity credential (`continuity_token`)

Resuming the **same contact** on a new browser session (e.g. after a page reload that lost the session token, or a deliberate "remember me" flow) requires a real credential, not the display id:

| Property | Rule |
|----------|------|
| What it is | Opaque, high-entropy secret (32 random bytes, base64url, 20–128 chars) — the **only** value that can bind a new session to an existing contact |
| Storage at rest | `contacts.continuity_token_hash` — SHA-256 hex digest only; plaintext is **never** persisted server-side |
| Client storage | Widget `localStorage` key `sitechat:continuity:{widgetPublicKey}` (`packages/widget/src/session/storage.ts`) |
| Issuance | Minted once per contact (`app_private.mint_contact_continuity_token`), returned as plaintext `continuityToken` in the session-create response **only the first time** a token is minted for that contact. It is never re-emitted afterwards — the client is expected to already hold it. |
| Binding rule | A **new** session (no session token, or an expired/invalid one) may link to an existing contact **only** by presenting a `continuityToken` that hashes to a stored `continuity_token_hash` in that workspace, **or** by presenting a valid session Bearer token that already has a `contact_id`. There is no other binding path. |
| Invalid/unknown tokens | Silently ignored — a fresh anonymous contact + session is created as if no token was sent. This avoids an oracle that would let an attacker enumerate valid tokens by observing different responses. |
| Rotation | Not rotated automatically while a hash already exists for the contact; the client keeps replaying the same localStorage value. |

`continuity_token` is the cross-session/cross-browser authorization binder. `public_id` (§3) is not, and never will be used as one.

## 5. URL privacy policy

Every URL persisted by the visitor identity system (`visitor_sessions.current_url` / `initial_url` / `landing_url` / `referrer`, `visitor_page_views.url` / `referrer`, and conversation `source_url` / `referrer` written from widget page context) is passed through the same allowlist sanitizer, enforced **in the database** (`app_private.sanitize_page_url`, defense in depth alongside the client/shared `sanitizePageUrl` in `packages/shared/src/visitor/page-context.ts`):

- **Keep:** `scheme://host[:port]` (http/https only) + `pathname` + the allowlisted UTM query params below.
- **Strip entirely:** the URL fragment (`#...`) — never parsed, never stored.
- **Strip all other query parameters** — this is an **allowlist**, not a blacklist. Only these five keys survive: `utm_source`, `utm_medium`, `utm_campaign`, `utm_content`, `utm_term` (`ALLOWED_UTM_PARAMS`).
- **Strip userinfo** (`user:pass@host`) from the authority component.
- Reject `javascript:` / `data:` / `vbscript:` and any non-`http(s)` scheme (returns `null`, e.g. so an internal SPA route `#` fragment or a `javascript:` bookmarklet URL never reaches storage).
- Bounded to 2048 characters after sanitization.

**Write paths covered:** session create/resume, page-view recording, visitor message send, attachment initiate (`widget_ensure_conversation_for_attachments`), and attachment complete (`finalize_visitor_attachment_message`). Message send and attachment paths only **backfill** `visitor_sessions.current_url` / `referrer` when those fields are still NULL — they must not overwrite a newer page-view context with stale client `pageUrl`.

**Consequence:** any secret, session id, auth code, tracking token, or PII a host page happens to put in a query string or fragment (e.g. `?token=...`, `#access_token=...`) is **never stored** by Site Chat, on the session, on the page-view trail, on the conversation source/referrer, or anywhere else. The operator dashboard cannot leak such values because they never reach the database — there is no redaction step to forget in the UI layer.

This policy applies uniformly to `current_url`, `initial_url`, `landing_url`, `referrer`, every `visitor_page_views` row, and widget-sourced `conversations.source_url` / `conversations.referrer`.

## 6. Page-view model, dedupe, and multi-tab

### 6.1 Storage

`visitor_page_views` stores a bounded trail:

- Required: `workspace_id`, `visitor_session_id`, `url` (sanitized per §5)
- Optional: `title`, `referrer` (sanitized), UTM fields, `contact_id`, `tab_id`
- Length bounds match session URL/title/UTM limits
- Operators see up to **20** recent views in conversation detail (`VISITOR_RECENT_PAGE_VIEWS_LIMIT`)

Deleting a session **cascades** to its page views. Deleting a contact sets `contact_id` to null on page views (session trail can remain).

### 6.2 Dedupe

| Layer | Behavior |
|-------|----------|
| **Server** | `widget_record_page_view` skips insert when the same session already recorded the **same (sanitized) URL** within the last **30 seconds** (`VISITOR_PAGE_VIEW_DEDUPE_SECONDS`). Response includes `recorded` / `deduped`. |
| **Client** | Widget throttles SPA page-view posts (~**1 second**, `VISITOR_PAGE_VIEW_CLIENT_THROTTLE_MS`) and skips hash-only navigations unless configured otherwise. |

Even when deduped, the RPC still refreshes session `current_url` / `current_title` / `active_tab_id` / `last_seen_at`. It does **not** touch conversations (see §8).

### 6.3 Multi-tab semantics

A visitor may have the widget open in several tabs of the same browser, all sharing one `visitor_sessions` row (same session token in shared `localStorage`):

- Each tab gets a stable **tab activity id** (`tab_id`) generated client-side and stored in **`sessionStorage`** (`sitechat:tab`), so it is unique per tab and cleared when the tab closes — it is a tab-activity identifier, not a fingerprinting signal.
- Every page-view POST includes the reporting tab's `tab_id`. The server writes it to `visitor_page_views.tab_id` and updates `visitor_sessions.active_tab_id` / `active_tab_seen_at`.
- **`visitor_sessions.current_url` / `active_tab_id` reflect whichever tab most recently reported a page view — there is no locked "primary" tab.** If a visitor has two tabs open and switches between them, the operator-visible "current page" flips to match the last one that posted, by design. This is a simplicity trade-off, not a bug: page-view history per tab is still recoverable from `visitor_page_views.tab_id`.

### 6.4 API

- Widget: `POST /api/v1/widget/page-view` (`Authorization: Bearer <session_token>`) → `widget_record_page_view`
- Privileges: **service_role only** at the database RPC (the Route Handler authorizes the session and validates Origin — see §11)

## 7. Identity update flows

### 7.1 Unsigned widget identify (current, `SiteChat.identify`)

The current `window.SiteChat.identify(...)` / `POST /api/v1/widget/identify` path is **unsigned**: the host page supplies name/email/phone/attributes with no proof of ownership. It is treated as unverified PII and scoped narrowly:

1. Resolve the **current** session by Bearer token within the workspace.
2. Ensure a contact exists on that session (create anonymous if missing).
3. Patch **only that session's current contact's** fields; merge attributes.
4. **Never** search or merge by email. There is no "find another contact with this email and reassign" step anywhere in `widget_identify_visitor`.
5. **Never** reassign the session or its conversations to a different (pre-existing) contact.
6. If the supplied email already belongs to a different contact in the workspace, the unique constraint on `contacts (workspace_id, lower(email))` raises a conflict, mapped to a generic `VALIDATION_ERROR`. **The caller's own contact is left untouched — they stay on their own (anonymous or previously-identified) contact.** An attacker who submits a victim's email cannot take over the victim's contact, session, or conversation history this way; at most they fail to set that email on their own contact.
7. Bumps `contacts.last_seen_at` (this is visitor activity — see §12) and touches this session's open/pending `conversations.updated_at` so the inbox refreshes (see §8).

RPC: `widget_identify_visitor` (service_role only). HTTP: `POST /api/v1/widget/identify`.

### 7.2 Verified identify (future, not implemented)

A **verified identify** path is planned to support durable, cross-session identity linking (e.g. "this browser is definitely `user@example.com`, they just logged into the host app"). It does not exist yet — no route, RPC, or schema for it ships today. Intended shape, so the interface contract is settled before implementation:

- The host backend (never the browser) computes a **signed assertion** proving it controls the claimed identity — either an **HMAC** over `{ workspaceId, email, issuedAt, nonce }` keyed by a workspace-specific secret shared with the host, or a **short-lived signed JWT** issued by the host and verified against a published/registered key.
- The widget forwards the signed assertion (never the raw secret) to a new endpoint (e.g. `POST /api/v1/widget/identify/verified`), which verifies the signature and expiry **server-side** before trusting the claim.
- Only a **verified** assertion may perform the durable, cross-session/cross-customer operations that unsigned identify explicitly must not: merging an anonymous contact into an existing identified contact by email, reassigning a session's `contact_id`, or migrating open conversations to the merged contact.
- Unsigned identify (§7.1) keeps its current, narrow, no-merge behavior indefinitely — verified identify is additive, not a replacement.

See [ADR-003](./adr/ADR-003-visitor-identity-model.md) "Verified identity (future)" for the full design rationale.

### 7.3 Operator edit

Dashboard agents update profile from a conversation:

- RPC: `update_visitor_profile(workspace_id, conversation_id, patch)`
- Requires **messaging role** (`owner` / `admin` / `agent`); **viewers are denied**
- Patch may include `name`, `email`, `phone`, `phone_e164` (at least one required)
- Ensures a contact exists on the conversation/session if missing
- Email uniqueness conflicts raise a clear error
- Lock order: conversation `FOR UPDATE` then contact `FOR UPDATE`
- **Does not bump `contacts.last_seen_at`** — an operator editing a profile is not visitor activity (see §12)

### 7.4 Attribute merge rules

`custom_attributes_json` / host `attributes` (unsigned identify only):

- Object of primitive values only (string, number, boolean); `null` deletes a key
- Max **50** keys; key ≤ 64 chars matching `[a-zA-Z][a-zA-Z0-9_.-]{0,63}`; string values ≤ 500
- Reserved keys rejected (`workspace_id`, `visitor_id`, `contact_id`, `public_id`, `session_id`, `id`, `__proto__`, `constructor`, `prototype`, etc.)

## 8. Realtime flow (operator sidebar refresh)

Identity and page context should appear in the operator inbox without a full reload. **Identify and page-view have different realtime signals** — page-view intentionally no longer bumps every conversation (write-amplification fix):

```
widget identify                         widget page-view
        │                                       │
        ▼                                       ▼
UPDATE contacts                        UPDATE visitor_sessions
        │                              (current_url, active_tab_id, last_seen_at)
        ▼                                       │
touch open|pending                              │
conversations.updated_at                         │
        │                                       │
        ▼                                       ▼
Supabase Realtime CDC on            Supabase Realtime CDC on
conversations (inbox channel)       visitor_sessions / contacts
        │                                       │
        └───────────────┬───────────────────────┘
                         ▼
        Dashboard sidebar subscribes to BOTH:
        - conversations (message/status changes)
        - visitor_sessions + contacts (identity/page context)
        On reconnect, schedules a catch-up refresh so any
        changes missed while disconnected are not lost.
```

- **Identify** (§7.1) still touches this session's open/pending `conversations.updated_at` — it is a low-frequency event and the inbox list benefits from re-sorting.
- **Page-view** (§6) does **not** touch conversations at all. Operators watching a conversation's live page context subscribe directly to `visitor_sessions` (by session id) and `contacts` (by contact id) UPDATE events (`VisitorSidebarLiveRefresh` / `subscribeOperatorVisitorContext` in `apps/web/lib/realtime/operator-subscriptions.ts`), not to the conversation channel.
- The subscription includes reconnect handling: on `connected`/`reconnecting` transitions it schedules a debounced refresh so a dropped-then-restored realtime connection doesn't silently miss context updates.

## 9. Host identify API (v1)

### 9.1 Shape

```js
window.SiteChat.identify({
  name?: string,
  email?: string,
  phone?: string,
  attributes?: Record<string, string | number | boolean | null>,
});
```

### 9.2 Semantics (v1)

| Rule | Detail |
|------|--------|
| Pre-init queue (implemented) | Calls made before the widget has finished loading are queued in-memory by the loader (`identifyQueue` in `packages/widget/src/loader/index.ts`) and flushed automatically once the iframe/session is ready — no calls are dropped |
| Workspace scope | Resolved from the embed public key / workspace of the loaded widget — not from caller-supplied workspace ids |
| Cannot set | `visitor_id`, `workspace_id`, `contact_id`, `public_id`, `session_id`, or other reserved identity keys via attributes |
| Transport | Loader → iframe → `POST /api/v1/widget/identify` using the existing session Bearer token; server validates Origin + session (§11) |
| Semantics | This is the **unsigned** identify path (§7.1) — no server-signed proof of the claimed identity, no cross-contact merge |
| Partial updates | Omitted fields are left unchanged; explicit `null` clears a field where supported |

Host pages must not invent or override visitor/workspace identifiers. The correlation id returned by init/identify (`visitorPublicId`) is server-issued and display-only (§3).

## 10. Session authentication

- The widget session credential is an **opaque, random Bearer token** (`session_token`, 32 random bytes, base64url) — **not** a JWT and not decoded/verified as one anywhere in the request path.
- Hashed at rest with SHA-256 into `visitor_sessions.session_token_hash`; the plaintext is never persisted server-side, only returned to the client once per session create/resume.
- Sent as a standard `Authorization: Bearer <session_token>` header on every widget API call (`getBearerToken` in `apps/web/lib/widget/responses.ts`); the widget database role never receives visitor identity as JWT claims.
- `app_private.resolve_visitor_session` re-hashes the presented token and looks up `visitor_sessions` by `(workspace_id, session_token_hash)`, checking `expires_at`.

## 11. Origin validation

Every widget mutation endpoint (`POST /api/v1/widget/session`, `/identify`, `/page-view`) applies the same check, in addition to embed-token verification:

- If the request carries a browser `Origin` header, it **must** match either:
  1. the `parentOrigin` bound to the embed token (host-page / CORS callers), or
  2. the Site Chat widget API origin (`request.url`) — the embed iframe is hosted on the app origin and issues same-origin fetches from there.
  A third-party Origin matching neither is rejected with `403 FORBIDDEN` (`requestOriginMatchesEmbed` in `apps/web/lib/widget/origin.ts`). This catches an embed token issued for one site being replayed from another, without blocking legitimate iframe API calls.
- Requests with **no** `Origin` header (some non-browser or same-origin-navigation cases) are allowed through this specific check — they still must carry a valid embed token and session, checked separately. Origin validation is defense in depth on top of, not a replacement for, embed-token + session-token verification.
- In development/test, a same-origin `localhost`/`127.0.0.1` fallback derived from `Referer` is permitted; this path is disabled outside `NODE_ENV=development|test`.

## 12. `last_seen_at` semantics

`contacts.last_seen_at` and `visitor_sessions.last_seen_at` track **visitor activity only** — session create/resume, identify, and page-view all bump them. Operator-driven mutations do not:

- `update_visitor_profile` (operator profile edit, §7.3) updates contact fields and `updated_at`, but **must not** and does not bump `last_seen_at`. An agent correcting a visitor's typo'd email should not make that visitor look "just active."

## 13. Privacy choices

| Choice | Behavior |
|--------|----------|
| No raw IP | `visitor_sessions` has **no** `ip_address` column; IPs are not persisted by default |
| No fingerprinting | No canvas, audio, WebGL, or cross-site fingerprint libraries |
| No raw User-Agent | Store parsed `browser_family`, `browser_version`, `os_family`, `device_type` only |
| `country_code` | Column reserved for **future trusted platform headers only**; never derive from IP geolocation in this path |
| PII isolation | Contact PII is workspace-scoped; RLS blocks cross-tenant SELECT |
| URL/query privacy | Allowlist sanitizer strips fragment + all non-UTM query params before storage (§5) |
| Page titles/URLs | Treated as untrusted text; sanitized/bounded; rendered safely in the dashboard |

See [PRIVACY.md](./PRIVACY.md) and [DATA-RETENTION.md](./DATA-RETENTION.md).

## 14. Non-goals (this foundation)

Out of scope for the identity + context foundation itself:

- Full CRM (deals, pipelines, lifecycle stages)
- Marketing automation or drip campaigns
- Precise geolocation or IP-based geo
- Verified identify (§7.2) — designed, not implemented

**Shipped separately as CRM-lite** (see [VISITOR-PROFILE.md](./VISITOR-PROFILE.md), [ADR-008](./adr/ADR-008-crm-companies-custom-fields.md)): tags, companies/accounts, typed custom fields with admin UI, and contact profile expansion. Host `custom_attributes_json` remains the identify-side bag and is not replaced by CRM fields.

## 16. Key RPCs and privileges

| Function | Caller | Notes |
|----------|--------|-------|
| `widget_create_or_resume_visitor_session` | service_role | Creates/resumes session by Bearer token or `continuity_token`; response includes `continuity_token` (plaintext, once) and `visitor_public_id` (display only) |
| `widget_identify_visitor` | service_role | Unsigned host/widget identify; patches current session's contact only; **no** email merge |
| `widget_record_page_view` | service_role | Page trail + 30s dedupe + `tab_id` / `active_tab_id`; does not touch conversations |
| `update_visitor_profile` | authenticated | Messaging roles only; does not bump `last_seen_at` |
| `app_private.ensure_visitor_contact` | internal | **Always creates a new anonymous contact.** No longer resolves or reuses a contact by `public_id` — continuity linking happens only via `continuity_token` inside the session RPC |
| `app_private.mint_contact_continuity_token` | internal | Mints and hashes a continuity token for a contact that doesn't have one yet; returns plaintext once |
| `app_private.sanitize_page_url` | internal | SQL-side URL allowlist sanitizer (defense in depth alongside the shared TS implementation) |

All `app_private` functions have `EXECUTE` revoked from `PUBLIC`/`anon`/`authenticated`; only reachable via the `SECURITY DEFINER` `public.*` wrappers above.
