# ADR-003: Visitor Identity Model

**Status:** Accepted (amended 2026-08-10 — security hardening)  
**Date:** 2026-08-10  
**Deciders:** Site Chat Engineering  
**Supersedes:** None (complements ADR-001)

---

## Context

The widget needs a durable notion of “the same visitor” across browser sessions, host-provided identify calls, and operator profile edits, without building a full CRM. Early schema already had a `contacts` table for identified people and `visitor_sessions` for browser tokens. We needed to decide how anonymous visitors, opaque client ids, custom attributes, and page-view context fit that model—and what not to build yet.

Constraints:

- Workspace isolation remains mandatory (ADR-001)
- Host `window.SiteChat.identify` must not set `workspace_id` / `visitor_id`
- Avoid fingerprinting and raw IP storage by default
- Keep operator inbox updates realtime-friendly

---

## Decision

1. **Contacts are visitor identity.** Keep the table name `contacts`; do not rename to `visitors`. Product copy may say “visitor”; schema and FKs stay `contact_id` / `contacts`.
2. **Sessions remain distinct.** `visitor_sessions` is browser/auth context (token hash, device/page/UTM fields, expiry). A contact may have many sessions over time. The session token is an opaque random value (hashed at rest); it is not a JWT and the visitor DB role does not receive identity as JWT claims.
3. **`public_id` is opaque, workspace-scoped, and is NOT a continuity binder.** Format `vis_` + 32 hex, generated by a column `DEFAULT` on `contacts` insert; unique per workspace; safe for localStorage and display; not enumerable; not a global user id. **`public_id` is never checked by any RPC to resume a session or bind a contact.** Its only job is client-facing correlation/display.
4. **`continuity_token_hash` is the cross-session binder.** A separate opaque secret (`continuity_token`) is minted server-side, returned to the client once, and stored only as a SHA-256 hash (`contacts.continuity_token_hash`). Presenting the matching plaintext (or a valid session Bearer token that already has a `contact_id`) is the *only* way a new browser session links to an existing contact. Unknown/invalid tokens are ignored rather than erroring, to avoid a token-enumeration oracle.
5. **Unsigned identify does not merge by email.** The current `widget_identify_visitor` RPC (backing `SiteChat.identify`) patches only the calling session's own contact. It never searches other contacts by email and never reassigns a session's or conversation's `contact_id`. An email already used by another contact in the workspace raises a conflict; the caller's own contact is left untouched. This closes an identity-takeover path where a malicious host page could call `identify({ email: "victim@example.com" })` to have the visitor's browser silently attached to the victim's contact/conversation history.
6. **Verified identity is a distinct, future capability.** Durable cross-session/cross-customer merging by email will only be permitted through a **verified identify** path that requires a server-signed assertion (HMAC or signed JWT) proving the host controls the claimed identity — see "Verified identity (future)" below. It is not implemented; unsigned identify's no-merge behavior is not a placeholder for it, it is the permanent behavior of the unsigned path.
7. **Attributes live in JSONB with bounds.** `contacts.custom_attributes_json` stores host/operator primitives with max key count, key/value length, and reserved-key rejection. No custom-field admin UI in this phase.
8. **Page views are a separate table with URL redaction.** `visitor_page_views` holds the trail with session FK `ON DELETE CASCADE`, optional `contact_id`, `tab_id` for multi-tab attribution, and server-side 30s URL dedupe. Every stored URL (page views and session `current_url`/`landing_url`/`referrer`) passes through an allowlist sanitizer (origin + path + `utm_*` only; fragment and all other query params stripped) enforced both in shared TypeScript and again in SQL.

Supporting RPCs: `ensure_visitor_contact` (always creates a new anonymous contact — no `public_id` lookup), `widget_create_or_resume_visitor_session` (continuity-token-based resume), `widget_identify_visitor`, `widget_record_page_view`, `update_visitor_profile`, `app_private.mint_contact_continuity_token`, `app_private.sanitize_page_url`.

### Verified identity (future)

Not implemented. Documented here so the interface contract is settled before anyone builds against it:

- The **host's backend** (never the visitor's browser) produces a signed assertion of identity — either an HMAC over `{ workspaceId, email, issuedAt, nonce }` keyed by a per-workspace shared secret, or a short-lived JWT signed by the host and verified against a registered key.
- The widget forwards only the signed assertion to a new verified-identify endpoint, which checks the signature and expiry server-side.
- Only a verified assertion may perform what unsigned identify explicitly must not: merge an anonymous contact into an existing identified contact by email, reassign a session's `contact_id`, or migrate open conversations to the merged contact.
- This is additive: unsigned `SiteChat.identify` keeps its current narrow, no-merge semantics regardless of whether verified identify ships.

## Alternatives considered

| Alternative | Why rejected |
|-------------|--------------|
| Rename `contacts` → `visitors` | Large rename churn across FKs, RLS, and docs for little clarity gain; “contact” matches CRM-adjacent future without forcing CRM now |
| Single table for session + identity | Couples token rotation to PII; breaks multi-session history |
| Sequential or email-derived public ids | Enumerable or PII-leaking; fails opacity requirement |
| Using `public_id` itself as the continuity/resume credential | The id needs to be safe to display, log, and hand to the host page for correlation — none of which is safe for a value that also authorizes session binding. Conflating "display id" and "auth credential" was the root cause this ADR's hardening amendment fixes. |
| Letting unsigned identify merge contacts by email | A host page (possibly compromised/malicious) asserting an email with no proof would let an attacker attach their own session/browser to any known victim email's contact and conversation history |
| EAV custom-fields tables + admin UI | Overbuilt for v1; JSONB bounds are enough for host identify |
| Embed page history in `metadata_json` | Harder to index, dedupe, cascade, and bound independently |
| Storing full page URLs verbatim (blacklist redaction on read) | Blacklists miss unknown params by construction, and any read-path redaction bug leaks whatever was stored; an allowlist enforced at write time in SQL cannot be bypassed by a new UI surface later |

---

## Consequences

### Positive

- Clear mental model: identity vs session vs conversation vs page trail
- Host and widget can resume visitors via the `continuity_token` credential, without fingerprinting and without treating a display id as a secret
- A leaked `public_id` (logs, screenshots, support tickets) has no session-takeover or contact-binding blast radius — it is inert outside of display
- RLS and email uniqueness stay workspace-local; unsigned identify cannot be used to pivot into another contact's data
- URL redaction means query-string/fragment secrets from the host page are never persisted, so there is no later "forgot to redact on display" bug class
- Page-view retention can be purged independently later

### Negative

- “Visitor” vs “contact” naming requires documentation discipline
- JSONB attributes defer rich field typing and admin UX
- Two client-facing identifiers (`public_id`, `continuity_token`) with different secrecy requirements must be kept clearly distinguished in code, docs, and future onboarding — mixing them up (e.g. checking `public_id` for authorization) would reintroduce the exact vulnerability this hardening fixed
- Deferring verified identify means legitimate cross-session/cross-customer identity merges are not yet possible; customers wanting that must wait for the verified path

### Follow-ups

- Verified identify (HMAC/JWT-signed assertion) — see "Verified identity (future)" above
- Retention purge jobs (`settings_json.privacy.visitorDataRetentionDays`)
- Export/delete UX
- Optional CRM/company/custom-field expansion (explicit non-goal now)
